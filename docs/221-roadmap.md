## Design basis

**Pattern:** canonical raw-resource caching with database leases, sorted bounded batch acquisition, owner-fenced publication, and projection after retrieval. Reuse `getOrRefresh` through a batch-aware store adapter; do not create another lifecycle or hold a transaction across provider HTTP. Retain the existing outer player-view cache and weather callback. The raw odds callback beneath that cache becomes shared with discovery.

**Alternatives:** process-local Promise coalescing fails across instances; player or market-set identities duplicate upstream work (81,900 market-set identities versus 240 per-market identities on the fixture); independent per-market refresh loops turn discovery batching into multiple paid requests; a second Redis/cache lifecycle adds infrastructure and competing ownership. Replacing the whole view cache with raw odds would change weather coalescing and observation behavior. The approved extension avoids those changes.

**Targets:** two independent instances and separate-process proof; PostgreSQL 18.6, lane-2 standard, 512 MiB; 20 independent leaders; 20 events × 12 registry markets = 240 raw resources; synthetic logical payload ≤8 MiB, reporting physical storage separately. A fresh raw-cache hit uses one SELECT and no claim/publish; a successful uncontended leader uses two pre-provider SQL statements and one publication. One provider request covers its owned missing-market batch. Followers perform no GCRA/credit mutations; their reads and failed lease claims remain database work. #221 adds no admission/accounting implementation.

The fixture is not a production event-catalog, response-size or retention cap. Existing per-player view rows remain in addition to the 240 raw entries. No hosted latency target is certified here. The approved #61 full warm pre-provider deadline is 90 ms. Checkpoint 1 will report this planning allocation: **four cache statements 10 ms + admission 53 ms + headroom 27 ms = 90 ms**. The aggregate work target is p95 ≤63 ms in each repeated round, leaving 30% headroom. This allocation is a design budget, not a measured pass: local raw-cache timings exclude the outer cache, and #220 admission p95 reached about 58 ms. Full-path measurement must establish whether the allocation holds; report misses rather than relax the deadline. Historical targets and #220 observations remain historical evidence.

**Requirement reasons:** canonical server-derived identities prevent client filters manufacturing paid work; projection after shared retrieval prevents another player's line leaking into a response. Sorted row locking prevents overlap deadlocks. Freshness rechecked under lock closes stale-read races. Owner fencing blocks obsolete publication, renewal and release. A pre-send database claim timestamp survives publication failure and prevents immediate repeat paid attempts. Cooldown without a published payload reports unavailable, never fabricated freshness; prior payloads remain explicitly stale. Separate caller TTLs preserve live/discovery freshness. Startup capability detection prevents queries against absent columns; metadata-query errors refuse readiness rather than silently permit legacy paid work. Proposal-only DDL preserves frozen migrations. No automatic ambiguous-outcome retry prevents invisible repeated paid work; a lease cannot promise upstream exactly-once execution after a lost response.

**Assumptions:** NFL, fixed US provider region/format/account and existing market validation; player/bookmaker/direction are view filters. New upstream selectors require identity review. Client abort is bounded at 20 seconds beneath a 30-second lease with renewal; a paused worker checks lease validity before starting its callback. This does not prove an external provider stopped processing an already accepted request. No application credentials, hosted resources or real provider calls were used.

## Qualified schema and lifecycle

`packages/db/proposals/221_shared_odds_cache.sql` adds nullable `refresh_owner`, `refresh_lease_until`, `refresh_claimed_at` to `event_market_odds_cache` and four claim/renew/publish/release functions. Existing payload/fetched-at nullability is unchanged. Cold claims insert an empty placeholder with epoch freshness, never a fresh observation.

Canonical, deduplicated batches contain at most 12 validated markets. Sorted row locks prevent lock-order deadlocks. Partition stale keys under the locks: exclude per-key 20-second cooldown keys from the eligible set and return their stale/unavailable status; claim eligible keys without letting a cooldown key block the batch. Active owners remain fenced and are never fetched over. Define follower handling for active leases separately from cooldown exclusion; do not hold a partial batch while waiting for another owner. Fresh slices are returned from the locked claim result; only owned missing slices are fetched, then combined for the caller. Publication is atomic and requires matching unexpired ownership for the complete owned set. Renewal/release cannot affect a successor. Claim time is retained when ownership is released and gates every caller for exactly 20 seconds per key; caller TTLs inspect fetched_at only. A missing market in a successful provider response publishes an empty slice, matching main, and is distinct from an unpublished placeholder. The SQL proposal now implements the approved fixed per-key cooldown and passes the amended checkpoint-2 cases. The archived prototype/initial receipts retain the superseded all-batch, caller-TTL policy as historical evidence. Preserve earlier receipts unchanged as historical evidence.

At startup, check the three nullable typed columns and all four function signatures once. Current/partial schemas select original functions; complete schema selects the shared adapter; query failure refuses readiness. There is no runtime flag or per-request capability query. Activation needs a separate schema release plus restart/drain plan: already-started legacy workers do not switch themselves when DDL appears. Legacy instances write without fencing during a rollover, so duplicate provider sends and unfenced publication can occur while generations overlap. This roadmap requires draining old instances before shared-path activation to preserve the ownership contract; accepting overlap instead needs an explicit owner exception. The activation sequence is: quiesce paid entry points, drain in-flight legacy work and prevent new legacy invocations, apply the separately approved proposal, start schema-checked new instances, verify shared routing, then reopen traffic. Stop if the hosting deployment cannot guarantee that drain. Mixed-generation activation has not been qualified by this spike.

The prototype shortened follower waits to accelerate behavior checks. Permanent integration retains existing 250 ms polling / 45-second maximum wait unless separately reviewed. Existing polling can issue both a read and a failed claim each turn; final tests count follower reads, failed claims and renewals at the real 250 ms polling / 45-second wait settings (controlled time may drive deterministic tests without changing those settings), not describe followers as zero-SQL. Accelerated follower tests do not certify the production polling bound or a full application deployment.
